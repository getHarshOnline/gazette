# VS Code integration qualification

Use this page when changing or qualifying the extension. The [developer integration guide](../vscode.md) owns loading the local extension and its selection/session contracts; [product help](https://rawthoughts.in/gazette/write-with-feedback/) owns writing a publication. The following fixture descriptions and historical observations retain their original scope. They are not a fresh editor-host result.

The editable implementation is TypeScript under [src/](../../integrations/vscode/src/extension.ts), compiled to CommonJS under ignored **dist/**. The package entrypoint is **dist/extension.js**; the superseded CJS source implementations are removed. The [compiler configuration](../../integrations/vscode/tsconfig.json) enables strict checking, exact optional properties, unchecked-index checks, explicit override checks and no emission on errors. TypeScript 5.9.2 and the VS Code 1.96.0/Node 20.17.0 declaration packages are exact development dependencies; the runtime language client remains pinned at 9.0.1. No bundler or handwritten semantic-model catalogue is introduced. **npm run typecheck** validates the declarations and implementation; **npm run build** emits the extension; **npm run check** also runs the tests against the emitted modules. The initialization shape follows the Rust LSP owner. Standard document symbols, workspace identity hover, reference completion, selected cross-document definition/reference results and heading/footnote queries use standard LSP; richer custom views require their own Rust-owned contracts only when implemented. Resource-input completion is likewise forwarded unchanged from the native LSP, including compiler-proven output-route data. Structured page-resource collisions and `documentation_validation_incomplete` evidence retain their diagnostic data through the version-pinned VS Code bridge. The documentation payload keeps manual routes/source selections and generated-reference navigation distinct; incomplete closure is not presented as Mintlify validation success.

[Settings](../../integrations/vscode/tests/settings.test.cjs), [source capture](../../integrations/vscode/tests/sourceCapture.test.cjs) and [lifecycle](../../integrations/vscode/tests/workspaceLifecycle.test.cjs) and [navigation](../../integrations/vscode/tests/navigation.test.cjs) and [diagnostic](../../integrations/vscode/tests/diagnostics.test.cjs) Node tests exercise the compiled extension modules with controlled editor/transport doubles. The [file-integration tests](../../integrations/vscode/tests/provider.test.cjs) separately check the installed client's registration order and exercise actual pinned JSON-RPC packet delivery to the replacement handler. Strict typechecking, compilation and the complete Node suite are the current local gate. An offline npm package dry-run included the README, package metadata, emitted modules and source maps but is not VSIX packaging proof. These checks do not establish native language-server or real editor-host execution.

The [application command fixture](../../integrations/vscode/tests/applicationCommands.test.cjs) exercises the compiled real controller with editor/transport doubles: every named CLI-family route, capability-first dynamic catalog selection, bounded guided and advanced schema projection, distinct folder sessions, exact multiline arguments, no default permission choice, effect-profile presentation, concise postconditions, explicit retained-receipt opening, stale/cancelled request refusal, raw native failures, post-dispatch receipt preservation, failed delivery and cleanup/replacement guards. The [transport fixture](../../integrations/vscode/tests/applicationSession.test.cjs) owns native carrier behavior separately. These new paths require their own combined native/editor qualification; the earlier authoring-host result below does not establish application-operation acceptance. Every hidden `gazette.application.<cli-family>` command also has an exact `onCommand` activation event checked against the names-only route projection. Cold programmatic use therefore activates the extension without contributing all specialist operations to the Command Palette or activating Gazette globally. The combined TypeScript build and Node suite cover command and carrier boundaries without fixing acceptance to a historical test count or host version. The separate `npm run test:live-catalog` gate starts an exact selected Gazette executable, discovers its current catalog, verifies every named CLI-family route and passes every descriptor through the same unique-name binding and inert schema projection used by the controller. The executable Rust interface test independently compares the route catalog to live CLI help, every material CLI mode and `tools/list`, and also checks each advertised LSP semantic against its named MCP authoring projection. This is not by itself a real editor-host result.

The [host fixture](../../integrations/vscode/tests/host.cjs) is for an existing VS Code executable, isolated temporary user-data/extensions directories and a disposable workspace named **gazette-vscode-proof.\*** under the host's selected temporary directory. Launch a local `.code-workspace` file with exactly two initial folders: the disposable configuration root first and its empty `host-sentinel` directory second. Converting a single-folder window into a multi-root workspace restarts the extension host, so it cannot be used as the start of this joined fixture. The test keeps the first root unchanged, adds and retires the actual selected owner roots, then retires only the sentinel before the application proof. It requires **GAZETTE_VSCODE_ISOLATED=1**, an exact independently built executable selected by **GAZETTE_TEST_EXECUTABLE**, and the extension development/test entrypoints. The fixture chains the selected-source authoring proof with a live application session that discovers MCP, prepares and explicitly runs a pinned local render, checks its exact output, proves denied reads and retained evidence, and leaves the source repository unchanged. Historical authoring-only host hashes do not certify this current combined fixture; a fresh combined host run is separate evidence.

The authoring portion uses actual editor commands for native diagnostics, selected content symbols, unsaved configuration definition/hover ranges, native reference completion and user-applied exact replacement followed by reanalysis, invalid-overlay replacement, captured-baseline restoration and unchanged source files. Position assertions use the actual editor buffer because VS Code preserves its CRLF policy when applying LF replacement text; plain-text hover assertions use the host's public `MarkdownString.appendText` representation.

Host acceptance requires all three `Gazette real editor proof`, `Gazette real distributed editor proof` and `Gazette real application proof` markers, together with no fixture failure in the renderer log and terminal process completion. A launcher exit code alone has also been zero on failed assertions. The distributed proof exercises 200 selected sources, three selected roots, modular configuration, an authored page larger than 64 KiB, unsaved cross-root consequences and root retirement. A successful run keeps settings and synthetic source writes in isolated disposable profiles/workspaces. It proves this local editor and application path, not actual owner-corpus authoring, VSIX installation, marketplace publication or remote/platform qualification.
