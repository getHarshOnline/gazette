# Qualify documentation generators

Use this page when changing a generator integration, validating its installed toolchain or interpreting a recorded provider check. To configure generation for an application, start with [Run a documentation generator](../documentation-generators.md). These fixtures exercise bounded owned inputs; their results do not establish fidelity for every project that uses the same generator.

## Required language coverage

Generated reference must support **Python, Rust, TypeScript and Go**, together with **OpenAPI/Swagger HTTP reference**. These are required application capabilities, not examples satisfied by accepting an arbitrary generator command. Each needs a qualified native generator and faithful target adaptation preserving applicable modules, public symbols, signatures/types, comments/examples, stable links and source/version attribution. HTTP OpenAPI reference is separate and cannot substitute for any language's library reference.

Use language-native tooling and established format tooling through the existing configured runner. Reuse Gazette's source capture, typed configuration, retained artifacts, limits, validation, assembly and interface projections. This is one composable pipeline, not separate language-specific publication systems or new handwritten language parsers. Extend the owning data structure or module when a real consumer needs it; share target-specific utilities only where semantics match.

All five generator routes use configured project sources and the same retained artifact/assembly path. Their reference sections are layered beside, not merged with, any explicitly selected authored manual sections in the applicable project module. Native generation stays target-independent; Mintlify conversion, manual packaging and final navigation assembly stay inside its adapter. Present gaps remain explicit:

| Python | Installed Sphinx 8.2.3 generates real JSON-builder output through the shared runner; public modules, signatures, cross-references and required companions reach the same local target; retained page, asset and fragment links close over that exact capture; the target rejects active elements and effect attributes before packaging | Arbitrary extension/import safety, general HTML sanitization, hosted rendering/asset behavior and a hosted-platform build remain separate qualification |

This table is bounded local capability accounting, not a claim that every project or hosted-platform route works. Missing tooling or a target limitation must fail explicitly and cannot silently omit a configured module or return a successful reduced publication.

## Five-generator qualification

The ignored-by-default [`documentation_domain_doc_cli`](../../interfaces/launcher/tests/documentation_domain_doc_cli.rs) fixture exercises all required routes in one real `gazette assemble-docs` call: Sphinx, stable Rustdoc, Node plus TypeDoc, gomarkdoc and go-swagger. Each generator is supplied through an explicit absolute test input; no path, package manager, home directory or operating-system prefix is compiled into Gazette. The fixture also requires independently supplied executable and complete version-stdout SHA-256 values, and refuses before generation if an observed identity differs. It does not turn observations from the same run into their own approval baseline.

The caller supplies these independent identities alongside the existing absolute tool paths: `GAZETTE_TEST_SPHINX_PYTHON_SHA256`, `GAZETTE_TEST_SPHINX_VERSION_SHA256`, `GAZETTE_TEST_RUSTDOC_STABLE_SHA256`, `GAZETTE_TEST_RUSTDOC_VERSION_SHA256`, `GAZETTE_TEST_NODE_SHA256`, `GAZETTE_TEST_TYPEDOC_VERSION_SHA256`, `GAZETTE_TEST_GOMARKDOC_SHA256`, `GAZETTE_TEST_GOMARKDOC_VERSION_SHA256`, `GAZETTE_TEST_SWAGGER_SHA256` and `GAZETTE_TEST_SWAGGER_VERSION_SHA256`. Values come from the selected qualification manifest or operator evidence, never from constants compiled for one host.

A local macOS run passed with five configured projects and five separately generated modules in one brand-owned documentation repository. It checked language/API semantics, generator validation where supported, navigation and link closure, then repeated the complete operation and obtained identical retained trees and bytes. The exact Git source and the configured owner destination were unchanged. This proves the local configured generation-and-assembly path on the observed macOS host; it does not prove arbitrary projects, a hosted Mintlify build, a GitHub push or public deployment.

Ordinary `cargo test` compiles these documentation-generator fixtures but does not run them. Real-generator qualification is an explicit `--ignored` test with caller-selected tools. A clean clone can therefore build and run its ordinary tests without Sphinx, TypeDoc, gomarkdoc or go-swagger, while release qualification still fails closed when a required selected generator is absent or mismatched.

### Reproducible Ubuntu gate

The `ubuntu-24.04 generated documentation` job in [`portable.yml`](../../.github/workflows/portable.yml) provisions the five selected generator routes outside Gazette, then executes the same ignored fixture:

- Python 3.13.7 plus Sphinx 8.2.3 and its complete hash-locked Python closure;
- stable Rustdoc from Gazette's pinned Rust 1.94.0 toolchain;
- Node 22.18.0 plus TypeDoc 0.28.20, TypeScript 5.9.3 and the npm lockfile-v3 integrity closure, including test-only `@mdx-js/mdx` 3.1.1 in Markdown mode, React 19.1.1, `rehype-raw` 7.0.0, `parse5` 7.3.0 and the frontmatter qualification graph;
- Go 1.26.6 plus `gomarkdoc` 1.1.0;
- Go 1.26.6 plus `go-swagger` 0.34.1 for OpenAPI/Swagger generation.

The setup actions are exact commit pins. Python and npm installs consume the checked-in locks. Go builds consume the checked-in `go.mod`/`go.sum` graph with `-mod=readonly`, exact direct releases and the selected Go toolchain; transitive modules cannot float without a reviewed lock change. Network access is confined to that explicit CI provisioning phase. The [`qualify-linux-providers.sh`](../../adapters/documentation/tests/qualify-linux-providers.sh) runner performs no installation, download or `PATH` discovery. It accepts exact absolute regular files, records each selected executable's SHA-256, records the complete stdout SHA-256 of the exact version command under the same cleared environment used by the fixture, and passes those values into the native identity checks. The generated fixture itself disables Go network/toolchain fallback and uses isolated ephemeral caches.

These run-scoped digests bind selection and detect replacement between the CI provisioning boundary and Gazette's execution; they are not independent approval, self-approval or permanent generator admission. This CI wrapper intentionally has weaker provenance than the fixture's release-qualification mode where expected digests come from a separately retained, owner-accepted manifest. Here the reviewed action pins, toolchain selection and Python/npm/Go locks own reproducible provisioning, while the same-run digests prove only that Gazette consumed those selected bytes without a substitution. A successful job proves the bounded fixtures on that Ubuntu runner only. It does not claim arbitrary-project fidelity, Mintlify hosting compatibility, a GitHub push, a paid/free entitlement or public deployment.

The Linux gate has not yet run on a hosted runner, and the macOS result does not stand in for Linux qualification.

The shared target request carries the existing immutable `TreeInput`, selected file-or-directory selection and declared native format. Imported artifacts and freshly generated output use this same boundary; assembly no longer discards companions before a target can inspect them. Artifact evidence records the exact selection, native content metadata (file size/digest or directory kind), and complete retained tree identity. A directory has no invented file digest: its scope is bound by the selection and complete capture identity. Those are input evidence, not permission to publish every companion or proof that a directory-based format is supported. Generation staging reuses the same acquired-source projection instead of building a second tree-selection path. No generator rerun or native reread occurs during target assembly.

## Native TypeScript qualification fixture

The [TypeDoc qualification runner](../../adapters/documentation/tests/qualify-typedoc.mjs) is a bounded generator qualification fixture. It requires already installed TypeDoc **0.28.20**, its complete npm lockfile-v3 package tree, an independently retained lock SHA-256, an explicit Node executable, and an existing Gazette executable. It performs no installation, download, Cargo build or generator configuration. Missing or mismatched tools fail; copied synthetic JSON cannot satisfy this fixture.

```sh
/absolute/node adapters/documentation/tests/qualify-typedoc.mjs /absolute/gazette /absolute/node /absolute/tool-root/node_modules/typedoc/bin/typedoc /absolute/tool-root/package-lock.json <retained-lock-sha256> /absolute/git
```

The runner reads the lock and installed package manifests, checks exact versions, and records/rechecks a bounded identity of the installed `node_modules` tree. The root lock must select one exact `engines.node` release, and the Node executable running the fixture must report that same release. The current qualification accepts Node 22.18.0 and rejects the available Node 26.3.0 executable before generator work. That observation supplements Gazette's executable-byte pin; it is not a verifier of npm tarball integrity, an independent admission of that lock, or a sandbox. The selected Node must also run the fixture itself. No ambient executable lookup or implicit plugin installation occurs; Git is a separate explicit absolute input used only to create and pin the owned source fixture.

It commits only the owned fixture's [API](../../adapters/documentation/tests/fixtures/typedoc/src/api.ts) and [model](../../adapters/documentation/tests/fixtures/typedoc/src/model.ts), with their [TypeDoc options](../../adapters/documentation/tests/fixtures/typedoc/typedoc.json), [TypeScript configuration](../../adapters/documentation/tests/fixtures/typedoc/tsconfig.json) and [package metadata](../../adapters/documentation/tests/fixtures/typedoc/package.json), in a disposable repository, then invokes the existing **`assemble-docs --local` command with `--allow-execute`**, not a separate generation command. The configured recipe selects the retained TypeDoc options file, native `--json` output, exact source pin and brand-owned documentation destination. Gazette performs native generation, capture, Mintlify assembly and separate local target staging.

Assertions require two public modules, a generic interface/property, a union, generic function signature, overloads, comments/examples, a resolved symbol link, source locations and package version. The actual generated JSON must survive Mintlify packaging byte-for-byte with the same reported digest and a navigation reference. Original and retained source bytes must remain unchanged, and the configured brand destination must not be created. The fixture intentionally uses [explicit TypeDoc entry points and no plugins](https://typedoc.org/documents/Options.Input.html) and [native JSON output](https://typedoc.org/documents/Options.Output.html).

Only a successful native run may report `native-typedoc-fixture-qualified`. Success removes only the runner's fresh temporary tree; failure retains it with its native stages for inspection and never retries. Neither outcome establishes arbitrary TypeScript coverage, cross-project link fidelity, hosted rendering, public admission, free-tier entitlement or publication.

The provider gate installs TypeDoc 0.28.20 and TypeScript 5.9.3 from the integrity-locked npm closure, selects the regular Node 22.18.0 executable, binds their current executable/version and lock identities, then validates the real artifact and retained package observation in the same run. The authoritative lock digest lives in `tools/distribution-evidence.toml`; run-local output hashes qualify only that execution and never a permanent global installation.

The local Mintlify adapter accepts the bounded TypeDoc serialization profile only at `schemaVersion = "2.0"`. Nonnegative numeric references must resolve inside the retained artifact. Its [target contract](../mintlify.md) distinguishes TypeDoc's unavailable-symbol sentinel, retained package-relative symbolic identities and explicit external links. Admitting an unresolved symbolic identity preserves its meaning; it does not establish a local symbol page or cross-project resolution. Generator, adapter and hosted proof remain separate.

## Native Rust proof

The [qualification runner](../../adapters/documentation/tests/qualify-rustdoc.mjs) invokes only the [owned dependency-free fixture](../../adapters/documentation/tests/fixtures/rustdoc/library.rs). It takes two explicit absolute Rustdoc executable paths, writes into a fresh temporary directory, limits each process to 30 seconds and 1 MiB captured output, and removes only that temporary directory afterward. It does not run Cargo, project build scripts, procedural macros, package installation or networking.

```sh
node adapters/documentation/tests/qualify-rustdoc.mjs /absolute/stable/bin/rustdoc /absolute/nightly/bin/rustdoc
```

The real generators passed assertions for module paths, public symbols, generic parameters, struct fields, borrowed function signatures, enum variants, re-exports, trait members, documentation examples, an intra-doc reference and source/version attribution. The JSON fixture deliberately gates schema 57. Rustdoc preserves the backticks in the intra-doc link key; consumers must read the actual model rather than guess its spelling. Numeric item IDs are not Gazette stable symbol identities. The generator-only test does not establish arbitrary Rust coverage, deterministic publication bytes, Mintlify rendering or a deployed site; target conversion and local Markdown/HTML rendering have the separate proof below.

### Static Rustdoc target proof

A subsequent [public-adapter fixture](../../adapters/mintlify/tests/rustdoc.rs) executes installed Rustdoc against the same owned Rust library, captures its actual complete output and passes the selected crate directory through the existing Mintlify target. It accepts a `RUSTDOC` executable override or the installed `rustdoc`, fails if unavailable and performs no installation or skip. This target-boundary test does not substitute for production generator-launch or process-custody qualification.

The native adapter tests run under both the stable Rustdoc 1.94.0 and a nightly Rustdoc, alongside the focused adapter unit tests. They preserve generic/borrowed signatures and linked types, examples, fields/variants, traits, inherent methods and associated items, reexport identity, nested module navigation, cross-module and explicit external links, exact source text, notable-trait sections, embedded MathML and type-alias implementations with distinct section destinations. All emitted local page and fragment links close, including source ranges; identical retained input produces identical target bytes despite a subsequent native-file change. Native generation itself was not claimed deterministic from this repeated-adaptation check.

The library fixture’s retained target was materialized only inside an owned disposable directory. With Rustdoc 1.94.0 and pinned Node 22.18.0, the exact npm-lock-v3 test graph compiled all fifteen emitted `.md` pages with `@mdx-js/mdx` 3.1.1 in explicit Markdown mode and `rehype-raw` 7.0.0, evaluated them with the React 19.1.1 JSX runtime and server-rendered each page. Independent `parse5` 7.3.0 inspection required full text, element and attribute parity against the parsed HTML tree. All fourteen `docs.json` navigation routes resolved to exactly one rendered page; rendered local page and fragment references also closed. The Rust adapter fixture independently checks complete exact HTML-body retention through native Comrak parsing, source-text fidelity and every local page/fragment target. The runner removes its disposable directory and does not install tools, fetch resources, initialize Git or contact Mintlify. This is local Markdown/HTML syntax, rendering, tree-parity and repository-structure evidence, not Mintlify's hosted renderer, extensions, build service, account, GitHub integration or deployment.

The adapter emits controlled Markdown with title frontmatter and escaped inert HTML from native formatted reference content, not a second Rust syntax printer or arbitrary MDX. The bounded profile and explicit unsupported cases belong in the [Mintlify Rustdoc profile](../mintlify-formats.md#rustdoc-html-directories). Locked local Markdown-mode compilation, HTML-tree parity and React server-rendering are qualified above; Mintlify's hosted parsing/rendering and platform-build proof remain unavailable. Foreign trait implementors, unqualified native page/content forms, broader cross-project fidelity and full Rust support remain incomplete. Rustdoc JSON is not adapted by this target.

### Actual SDK references and external documentation roots

The actual Pale and Gazette SDK reference outputs have passed the same local target and rendering checks, the Gazette one after the explicit native input preparation below. Both ran on a newer Node than the Node 22.18.0 provider gate, with the installed Markdown/React/HTML test graph, and passed full HTML-tree parity and local page/fragment closure. These checks establish reference-only assembly and local rendering, not a joined authored manual, a configured production generator job or Mintlify's hosted renderer.

Native generation can finish successfully with unresolved links inherited from dependencies, even with `-D warnings`. Gazette's SDK exposed Rust-shaped `tracing` links and documentation from two different `itertools` versions; the older dependency also declared a stale external documentation root. A crate-name mapping alone cannot represent both versions. The adapter keeps rejecting unresolved links instead of guessing where they belong.

The successful Gazette capture used a nightly Rustdoc with `-Z unstable-options`, `--extern-html-root-takes-precedence` and explicit `--extern-html-root-url` mappings. Cargo's artifact messages identified the exact compiled metadata for `tracing` 0.1.44, `tracing-core` 0.1.36 and `itertools` 0.14.0 and 0.10.5. Distinct aliases bound each metadata file to its versioned documentation root. Rustdoc applied those aliases only when four private, documentation-only `extern crate` imports loaded them in a prepared source export; passing the aliases on the command line alone, including `force,noprelude`, did not resolve the links in this toolchain.

That preparation was confined to the qualification export and restored afterward. The generated source pages accurately contain the prepared input, including those imports. This is evidence for an explicit preparation route, not pristine-source generation or an automatic Gazette feature. A maintained preparation step, its retained input identity and its configured generator job still need implementation and qualification before this route can be used in production. The separate, narrowly qualified BTreeMap destination correction belongs to the [Rustdoc format profile](../mintlify-formats.md#rustdoc-html-directories); other missing destinations remain errors.

## Integration obligations

### Native Swagger generation and validation

The [go-swagger fixture](../../adapters/documentation/tests/swagger.rs) runs the installed v0.34.1 executable against owned, dependency-free Go HTTP source through the existing generator. The successful capture preserves operation, parameter, model, response and security references, then passes the same tool's `validate` operation without changing the captured tree. Missing source refuses before execution. Invalid Go can make this generator exit successfully with an incomplete specification; selected native validation rejects that output while preserving generation success and validation failure separately. The shared native-process tests cover validator failure, changed input, rewritten output and added-companion refusal, and the SDK tests cover preservation of the exact validation tree and uncertain invocation in compact delivery. These transport checks do not broaden native format qualification.

Run this fixture with explicit `GAZETTE_TEST_SWAGGER` and `GAZETTE_TEST_GO_ROOT` absolute paths. It disables module/toolchain downloads and uses fresh local caches. This proves a bounded Swagger 2 generation/validation route, not Go library reference or general Go syntax checking. The SDK fixture carries that retained contract through the Mintlify conversion path, configured brand repository binding, private staging and deterministic reassembly. The Mintlify [Swagger conversion profile](../mintlify-formats.md#openapi-and-swagger) has explicit `swagger-json`/`swagger-yaml` input declarations and a separate original-schema/conversion/output-validation boundary. This establishes the documented bounded local conversion profile, not unrestricted Swagger compatibility or a hosted-platform build.
