# MCP maintenance and qualification

Use this guide when changing the tool catalogue, request handling or authoring bridge. Start with the checks below, then use the coverage tables to find the corresponding CLI and LSP behavior. The [MCP integration reference](../mcp.md) explains how clients connect and call tools.

## Check a change

From the repository root, run the protocol tests and the executable interface checks:

```sh
cargo test --locked -p gazette-mcp --lib
cargo test --locked -p gazette-launcher --test interface_coverage --test interface_evaluation
```

The library tests exercise descriptors, schemas, permissions and stateful handlers. The [interface coverage test](../../interfaces/launcher/tests/interface_coverage.rs) starts the real CLI, MCP and LSP to check their operation mappings. The [discovery evaluation](../../interfaces/launcher/tests/interface_evaluation.rs) checks which operations match the [example requests](../../interfaces/launcher/tests/fixtures/interface_intents.json). It uses deterministic lexical ranking; it does not predict a model or host's choices.

For a descriptor change, update its native registration and the corresponding request case, then run both checks. For a behavior change, add a regression beside the affected handler tests and check the matching SDK, CLI or LSP path. Include failure, permission and stale-state cases where the operation supports them. A catalogue entry alone does not test its dispatch or effects.

## Descriptor and dispatch changes

When adding or changing a tool, derive input and result projections from their native typed owners and keep one catalogue for discovery and `tools/call` dispatch. Discriminated queries need their actual alternatives in the schema; a generic object with prose is insufficient. Do not maintain a second semantic field catalogue. Output schemas must include native failure shapes and output-limit alternatives wherever structured results can return them. Preserve required nullable values separately from omitted optional fields.

Effect annotations describe the widest admitted request path. Coordination-file creation is an effect, registry replacement is destructive, and fresh directory or generation creation is not safely retry-idempotent. Separate effect modes when one descriptor would obscure the permission the caller must grant. Keep class, potential-effect facets, hints and dispatch disposition coherent; the integration reference owns how clients interpret them.

## Application operations

The current `gazette mcp` implementation is a bounded protocol projection over the Rust SDK. It does not parse command-line output, implement another compiler, or discover unselected native sources. Its discoverable tools cover supplied configuration, supplied Markdown, explicitly held authoring buffers, opt-in local source/TOML reads and supplied release-signature verification, explicit native destination observations and local artifact verification, complete local site rendering and explicitly permitted local preparation, publication inspection, private review and registry projection, selected composition acquisition, metadata checking, template compilation and pinned site-documentation acquisition/parsing, plus existing-store, journal and registry inspection, managed diagnostic observation history, complete native preparation/signature joins, immutable release transaction history and explicit held release sessions over the same native SDK writer. Four separate store tools project fresh initialization, backup, pinned verification and detached recovery with native permissions and shared bounded output delivery. `check_documentation` resolves a site's brand-owned destination and ordered authored-manual/generated-reference intent from supplied workspace bytes through the same target preflight, without acquisition, generation, assembly or native effects. `assemble_docs` projects the subsequent configured manual/reference acquisition, explicitly permitted native generation, shared target assembly and bounded fresh retention. Its optional `preparation` selection instead records the assembled generator-input tree through the shared durable local staging path, with independent journal permissions and exact recovery-pin delivery; this is not hosted-output certification. `reconcile_registry` separately projects complete native registry replacement; CLI and MCP share bounded delivery preserving original writer, write and close outcomes. It does not initialize, migrate or release the store. `stage` separately creates and synchronizes one fresh private source composition through the existing SDK, with independent read/write permission and bounded original-evidence delivery. It never replaces sources or an existing stage. Authoring tools change process-local buffers without native I/O. Supplied workspace checks do not open configured repository paths. Separate local-read source tools call the native SDK against exact selected roots; they do not write, fetch, migrate, sign or release anything. Storage inspection separately requires permission for possible SQLite coordination-file maintenance, never SQL writes. `inspect_materialization` separately reads durable configured-output ownership and pending intent at an exact historical destination coordinate through the shared SDK. It acquires no writer, opens no output directory and does not retry or reconcile effects. Historical completion is not current filesystem evidence. `materialize_sites` separately renders one complete selected publication set and writes its configured existing output directories through an already-held ordinary writer session. It requires independent output-write and durable-history permissions, exact distinct per-site operation IDs and complete-set preflight. It preserves original custody on delivery failure and leaves explicit session inspection and close with the caller. See [configured output materialization](../output-materialization.md). `materialize_docs` uses that same held-writer boundary for the configured documentation repository, consuming its retained manual/reference assembly rather than Theme-rendered pages. Assembly, configured output, preparation and release remain separate operations. The separate `prepare_sites` tool can create retained stages, journal phase records and detached Git worktrees; a configured checker and an explicitly selected coordinator anchor each require their own permission. It is not certification or release. `qualify_sites` separately runs complete-set technical qualification without release preparation: no stages, journal/store writes, Git preparation or push. Each selected site requires an explicit candidate-policy check. Checkers and explicitly selected generators remain unsandboxed processes with their own permissions; a lost report does not erase those possible effects.

The current CLI application operations and LSP handlers have routes below. This is coverage of the present native interfaces, not completion of the broader publication/editor goal or qualification of every integration. Reuse shared application/SDK and selected-source behavior; do not duplicate semantics, parse command stdout, tunnel an opaque LSP conversation, or hide all operations behind a generic shell/command tool.

## Authoring and LSP mappings

The [LSP dispatcher](../../interfaces/lsp/src/server.rs) currently exposes selected workspace/content buffers, full-text versioned overlays, current diagnostics, workspace declaration/Markdown heading symbols and selected-source TOML, heading/footnote and publication-link definition/reference navigation, plus workspace identity hover and native workspace, editorial, authored and symbolic reference replacement. MCP exposes these through the same SDK session owner. Schema-derived missing-key, closed-literal and hover facts are available for workspace TOML, explicit authored TOML frontmatter and the reduced schema of exactly selected legal-source bindings through the same SDK session. LSP quick fixes and MCP `authoring_review_repair` both project reviewable replacement proposals from an exact current Gazette diagnostic; neither applies an edit or runs a command. Rename, semantic tokens and formatting are not current LSP capabilities and must not be falsely advertised as existing tools.

The one-shot supplied-string `workspace_field_origin` and `workspace_composition_origin` tools remain available separately from session-bound `authoring_origin` and LSP `gazette/origin`.

## What the executable checks cover

The executable interface-parity gate starts the real CLI, MCP and LSP surfaces. It compares every non-launcher CLI command and material mode to MCP discovery, then compares the same command-family projection used by VS Code, and checks every LSP-advertised authoring semantic against its named MCP route. VS Code still resolves schemas and effect hints from the live MCP catalog; the projection contains names only and cannot become a second application implementation.

The executable interface-evaluation fixture exercises this discovery surface against representative workspace, build, documentation, authoring, preview, store, observation, recovery and release intents. Its deliberately simple offline lexical baseline scores name, title, description, capability, intent and prominence tokens with fixed weights and deterministic name-based tie-breaking. It requires the intended operation in the top three, separates a named confusable operation, keeps protocol read-only intents from ranking a mutating operation first, checks canonical closure for selected actions and measures the selected schema bytes against the complete live catalog. This is a reproducible descriptor regression, not a claim about an MCP host, language model or private tool-search extension.

When adding an operation, keep its discovery, schema and dispatch tests together. Exercise bounds, refused effects, stale buffers and session closure in the matching behavioral test. For an operation that can write or retain output, include the lost-response path so a client can recover the original result without repeating the effect.
