# Write build files to a directory

<a id="write-an-exact-local-generation"></a>

Update the directory configured for a publication or a developer docs site. Start with a complete [publication render](local-rendering.md) or [documentation assembly](mintlify.md). Gazette compares the generated files with the existing directory before writing, leaves files it does not manage in place, and checks the resulting tree.

Choose how the caller should track generated files:

| Task | Entry point |
| --- | --- |
| Write one publication and retain its receipt in the current process | [Receipt-only Rust API](#configuration-names-the-destination) |
| Keep generated-file ownership across supported journal reopen | [Journal-bound writer](#durable-ownership-uses-the-existing-private-journal) |
| Update the configured developer-documentation repository | [Documentation materialization](#documentation-uses-the-same-writer-not-the-theme-renderer) |
| Invoke publication materialization from a CLI or MCP client | [CLI and MCP operation](#cli-and-mcp-use-the-same-guarded-operation) |
| Plan every destination before writing a publication set | [Complete-set operation](#a-set-checks-every-destination-before-writing) |

The destination must already exist. Durable history requires its own journal
permission. Materialization neither prepares a release nor publishes the output.

## Configuration names the destination

Set `output.directory` to an existing directory separate from every source root. Gazette refuses an omitted setting, a missing directory or a relative path in detached configuration. It does not use the working directory or create a stage in its place. Keep exclusive local control of that directory while planning, writing and using the result.

With the SDK's `native-local` feature, use the complete `PublicationRender`:

```rust,ignore
let plan = gazette_sdk::build::plan_output(&rendered, None, limits)?;
// Inspect plan.root(), binding(), observed(), expected() and changes() before granting effects.
let receipt = gazette_sdk::build::materialize_output(plan, true)?;
// receipt.inventory() is the complete verified tree, including preserved user files.
```

Passing `false` refuses the write. The plan borrows the generated bytes. The writer does not reopen sources or compile again. This in-process result is separate from fresh staging and the journal-backed CLI/MCP operations.

`OutputObservation` contains the complete inventory excluding Git administration and its `OutputBinding`. Use `plan.observed()` for the inventory and `plan.binding()` for the canonical path, held directory's device/inode and the root `.git` entry's kind and device/inode, if present. The writer checks the same binding before writing and after reading back. A new directory or Git entry at the same path fails even if every generated file is identical.

## Replace only files Gazette already manages {#a-render-alone-does-not-own-existing-files}

A fresh plan refuses a generated-file collision even when the existing file has identical bytes. A marker in the destination grants no ownership. Successful materialization returns a privately constructed `MaterializedOutput`; only that actual write/read-back receipt can identify a prior generation for the next plan:

```rust,ignore
let next = gazette_sdk::build::plan_output(&next_rendered, Some(&receipt), limits)?;
let next_receipt = gazette_sdk::build::materialize_output(next, true)?;
```

The site, configured directory and native binding must match the receipt. `receipt.binding()` retains the identity observed through the successful writer; a matching pathname and inventory alone do not transfer that generation to a replacement directory. Every prior generated entry must still be present and unchanged. Replacement and obsolete-file removal are limited to those entries; shared directories are never removed. Unrelated files remain in the complete expected inventory, and file/directory transitions are refused.

This receipt-only API is synchronous local evidence, not a serialized ownership manifest. Neither it nor the binding establishes custody after a process restart, namespace replacement or a gap in exclusive control. Device/inode observations are not an inode-reuse defence or cross-host fence. Use the separate journal-bound path below when generated ownership must survive a process lifetime; neither path supplies automatic interruption recovery.

## Keep generated-file history in the journal {#durable-ownership-uses-the-existing-private-journal}

The `native-local` SDK can bind configured output to the same already-held ordinary store writer used for other local journal operations. It does not acquire a release coordinator, publisher authority or a second writer:

```rust,ignore
let plan = writer.plan_materializations(&rendered_set, limits, evidence_bytes)?;
// Inspect every site plan before granting either independent effect permission.
let results = writer.materialize_set(
    plan,
    &operation_ids, // Exact site-key map; distinct caller-selected SHA-256 coordinates.
    gazette_sdk::build::MaterializationOptions {
        allow_write: true,
        history: gazette_sdk::store::MaterializationWriteOptions { allow_record: true },
        evidence_bytes,
    },
)?;
```

Every site requires a distinct operation coordinate. Missing, extra or duplicate coordinates refuse the complete set before any intent append or output write. Plans cover the complete selected set, aggregate inventories and aggregate private build-evidence budget. Native source, peer-destination and actual held journal/anchor roots are protected; a caller cannot substitute an asserted journal locator for the held provider's roots.

For each original operation the application records exact intent before filesystem effects: site, native output binding, preceding completed head, complete observed/expected inventories, generated subset and bounded acquisition/composition/render evidence. Successful native read-back must match that original binding and full expected inventory before a transaction records completion and advances ownership. Registry projection, output history and release history remain separate responsibilities.

A later writer can inspect the completed head and independently reobserve the destination to update or remove only unchanged previously generated entries. An old source locator in retained evidence is not permission to reopen that retired source. Unrelated user entries remain preserved. Equal stored intent replay returns history with `output: None`; it neither dispatches another write nor proves the current destination's bytes. Reconstructing a new plan is not automatically an exact replay of an old operation.

A pending operation blocks a new start at that destination. Changed native bytes before dispatch, partial filesystem effects, lost completion and uncertain journal persistence retain their separate evidence; none authorizes retry, cleanup or rollback. Restore adoption refuses unresolved materialization history rather than stranding or silently resetting it. The journal verifies linkage and representation, while the application retains ownership of filesystem policy.

These records survive supported writer reopen and backup. They do not establish exclusive output custody, protection against inode reuse, cross-host fencing or freshness of copied/restored journals. The destination must remain under trusted local control, and current ownership always requires native reobservation.

## Write the developer docs directory {#documentation-uses-the-same-writer-not-the-theme-renderer}

A retained `DocumentationAssembly` can plan output at its brand's configured `documentation_repository.path` through `build::plan_documentation_output`. The directory must already exist. An absolute coordinate remains explicit; a relative coordinate resolves against the retained native workspace owner, never the process directory. A detached supplied configuration cannot authorize a relative destination. Assembly alone still performs no configured-directory write.

For durable ownership, use the same already-held ordinary writer:

```rust,ignore
let plan = writer.plan_documentation_materialization(
    &assembly,
    &protected_roots,
    limits,
    options.evidence_bytes,
)?;
let result = writer.materialize(plan, operation_id, options)?;
```

The planner protects captured sources, generator stages and the held journal. It reuses the publication writer's collision, generated-ownership, intent, read-back and completion rules. Its evidence names the documentation artifact class, configured site and brand, repository, exact source/configuration identities, authored manuals, generated references and assembled tree; it does not fabricate a Theme-rendering record or hosted-output certificate. Materialization consumes retained bytes without rerunning generators or reopening manual sources. An exact historical replay returns `output: None`, while pending or changed ownership refuses further writes. This SDK operation does not imply that `assemble_docs` performs configured-directory materialization; its fresh retention and preparation selections remain distinct.

`gazette assemble-docs --local --workspace-json --site site:reference` reads the shared `WorkspaceInput` JSON object from standard input instead of supplied TOML. Select `kind: "local"`, an explicit `root` and a relative `workspace` file to retain the native workspace owner. The existing supplied form uses `kind: "supplied"` and `source`; it supplies no native owner for a relative destination. `--check` remains an effect-free supplied-TOML operation and cannot be combined with `--workspace-json`. Assembly and fresh staging still do not write the configured destination.

For MCP configured delivery, open an ordinary writer once and call `materialize_docs` with its `session`, an exact operation `id`, independent `allow_write` and `allow_record`, and `documentation` containing the same input as `assemble_docs`. Both documentation tools use the shared supplied/local `workspace` selector. Fresh `output_parent` and `preparation` retention are incompatible with configured materialization. The tool runs the native documentation sequence once and gives that retained assembly to the same held writer; it does not reacquire a writer or rerun generators to construct output.

The response keeps the original native documentation JSON alongside the output outcome, including generator jobs and retained paths when output planning or writing fails. Combined response capacity is checked before native work. If full output evidence cannot fit, the error retains documentation custody, the original session and header, the request digest and operation ID; missing evidence is not success or permission to retry. Explicit `inspect_store_session` and `close_store_session` own the remaining lifetime.

The direct CLI route is `gazette materialize-docs /absolute/private/journal --expected-header '<complete JSON header>' --operation <lowercase-sha256> --site site:reference --local`. It reads supplied workspace TOML from standard input, or the same supplied/local `WorkspaceInput` object with `--workspace-json`. Supply the independent `--allow-read`, `--allow-write-output`, `--allow-record-history`, `--advance-writer-generation`, `--reserve-local-coordination` and `--allow-coordination-files` permissions. Configured generators additionally require an explicit `--generator-parent`, `--allow-stage` and `--allow-execute`; these are not implied by output-write permission.

The CLI acquires one ordinary writer, consumes the same documentation operation once and explicitly closes that writer. Its JSONL frames retain the original and acquired journal headers, exact operation and request identity, native documentation JSON and the separate output/close outcomes. If materialization details exceed the response ceiling after a write, the incomplete frame still carries the original documentation response; it exits unsuccessfully, and durable history must be inspected before any further effect. A pending intent refuses a new write. Neither an unsuccessful exit nor lost standard output means rollback or permits automatic retry. This route has no fresh-output or preparation-retention alias: `assemble-docs`, staging, configured materialization and release preparation remain separate operations.

## Inspect history without acquiring a writer

`gazette inspect-materialization /absolute/private/journal.db --output-root /exact/historical/canonical/output --allow-coordination-files` reads the complete destination frontier. Add `--expected-header '<complete JSON header>'` to compare independently retained coordinates; omission is observation only. The equivalent MCP tool is `inspect_materialization`, with explicit `allow_read`, native `read` options and the same optional header.

The output root is the exact historical coordinate, not a write capability or an instruction to canonicalize/open a current directory. Inspection works when that directory no longer exists. It returns the completed head and separately unresolved intent under one verified database snapshot, never current output contents. SQL remains read-only; acknowledged SQLite WAL/shared-memory coordination-file maintenance may still occur. No writer generation, migration, repair, destination access or automatic retry follows an inspection.

## CLI and MCP use the same guarded operation

`gazette materialize-sites` reads one complete `LocalPublicationRecipe` JSON request from standard input. Supply the existing private journal directory, its independently retained complete `--expected-header`, `--local`, `--allow-read`, `--allow-write-output`, `--allow-record-history`, `--advance-writer-generation`, `--reserve-local-coordination` and `--allow-coordination-files`. Repeat `--operation SITE=lowercase-sha256` for every selected site, with a distinct caller-retained operation ID. `--help` states the independent recipe, render, complete-set output, evidence and response limits. Gazette acquires one ordinary writer, renders the selected set once, uses the shared complete-set planner and writer, then explicitly closes that same session. It does not acquire release authority.

The CLI emits bounded JSONL frames for reserved custody, acquired custody and the final outcome. Keep the request, journal path, original and acquired headers, request digest and operation IDs. Native failure and close failure remain separate. An oversized final result returns a compact `delivery_incomplete` frame, retains the original coordinates and exits unsuccessfully even if the native write completed; it never labels missing evidence a successful delivery. Lost stdout is not rollback.

For MCP, open an ordinary writer through `open_store_session`, retain its handle and acquired header, then call `materialize_sites` with that `session`, the same native `publication` request used by `render_sites`, a complete `ids` map, and independent `allow_write: true` and `allow_record: true`. Its `publication` still requires `local: true` and `allow_read: true`. The tool uses the already-held writer without reacquisition and returns the shared per-site materialization inspections or the exact render, plan or write failure. The session remains held for explicit `inspect_store_session` and `close_store_session`; a retained handle is custody evidence, not a guarantee that a failed writer remains usable.

Both carriers reserve compact recovery coordinates before acquisition or output effects. MCP returns an error outcome with those coordinates when a complete result cannot fit. Inspect durable history before any further effect; neither carrier retries, rolls back or turns a newly reconstructed plan into historical replay. An exact original-plan replay may return `output: null`; that reports retained completion, not fresh observation of destination bytes. CLI invocations that reconstruct a plan must use new operation coordinates rather than relabeling the new intent as an exact replay.

The existing `stage_rendered_site` and documentation staging routes still create fresh private children. They do not write a configured existing output directory and are not substitutes for this operation.

## A set checks every destination before writing

For a complete `RenderedPublicationSet`, `build::plan_outputs` checks all configured destinations before returning a plan. Equal, nested or aliased native roots are refused, and each later writer protects every other destination as well as the selected inputs. Missing configuration, a failed render, an unrelated prior receipt or any unsafe destination refuses the entire plan without output effects.

```rust,ignore
let plan = gazette_sdk::build::plan_outputs(&rendered_set, &previous_receipts, limits)?;
// plan.sites() retains every requested site's original plan and generated bytes.
let receipts = gazette_sdk::build::materialize_outputs(plan, true)?;
```

The set's entry and byte limits cover the sum of its complete observed and proposed inventories, including preserved user files. They are not a fresh allowance for each site. All plan observations are checked before writing, and each native writer rechecks its own observation at the effect boundary; preflight is not a lock.

Execution follows deterministic site-key order. A later failure stops subsequent sites and returns `OutputSetWriteError`: the full requested order, only the actual completed receipts, the failed site and its original attempted-path/residue evidence. A completed prefix is not set success. Unattempted sites are not silently removed, and neither completed nor uncertain writes are automatically retried or rolled back. This is local build-set handling, not release-set settlement.

## Git administration and user work stay outside the generated tree

A root `.git` directory or worktree pointer is held and rechecked but never traversed, copied or removed. The selected output directory must also lie outside any `.git` path component, including case variants and ancestor aliases that resolve into that namespace. This guard applies only to output; it does not alter source capture or classify arbitrarily named external Git administration directories. Nested or case-variant Git paths, links, special files, canonical path collisions and source overlap are refused. Files are installed through held directories and atomic native file-name transitions on Linux and macOS; replacing a file never truncates another hardlink to its old inode. The complete generation is not one atomic multi-file transaction.

Git-entry checks distinguish its identity from mutable metadata. A held pointer file is also checked for metadata changes during each synchronous observation or write, without reading or interpreting its contents. An administrative directory's identity is checked, but changes to its timestamps or contents are not treated as a replacement; Gazette does not inspect that subtree. These checks do not prove repository validity or custody between operations.

## Inspect an interrupted write {#an-incomplete-effect-is-not-a-successful-generation}

Before the first write, Gazette checks the complete destination again. If its root or Git entry changed, or any user or generated bytes changed, the plan fails without writing. If an error occurs after writes start, `OutputWriteError` records the cause, attempted paths in order and temporary files left behind. Some changes may already be present.

Inspect that state before another operation. Gazette does not roll back, delete leftover files or retry automatically. A successful read-back establishes the local files. The journal can remember which files Gazette generated; release preparation and approval are separate.
